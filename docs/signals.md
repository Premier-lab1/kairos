# Сигналы и скоринг s1

Черновик 19.10.2026 (ночная разработка), формула поправлена после ревью Fable. Скор — правила и статистика по накопленной истории, LLM только объясняет. Пороги и веса — стартовые, их надо проверить бэктестом на большей выборке.

## Когда считается сигнал

- Токен попадает в скоринг, когда у него есть упоминание CA шиллером (`mentions.token_id`), а первый шилл не старше `SIGNAL_MAX_AGE_HOURS` (6 ч).
- Скор пересчитывается в конвейере раз в `SIGNAL_INTERVAL_S` (60 с) для токенов, у которых появились новые упоминания после прошлого расчёта.
- Одна строка `signals` на (токен, `scorer_version`): `created_at` — первый расчёт, `updated_at` — последний, `score`, `confidence`, `features`, `n_shillers`, `first_mention_at`. Миграция `0005_signals.sql`.
- Сильный сигнал — `score ≥ SIGNAL_SCORE_THRESHOLD` (60, заглушка до бэктеста) **и** `confidence` не ниже `medium`. Бот рассылает сигналы выше порога пользователя (по умолчанию тот же) и только с `confidence ∈ {medium, high}` — защита от холодного старта, когда истории нет.

## Главное правило: никакой утечки будущего

Признаки на момент `t` (момент расчёта) строятся только из того, что было известно в `t`:

- упоминания с `tweet_time ≤ t`;
- исходы прошлых токенов, у которых горизонт закончился не позже `t`: `reference_time + horizon ≤ t`, и метка окончательная (`success`, `rug`, `dead`, `neutral`);
- сам оцениваемый токен в свою же историю не входит;
- базовые доли `b`, `b_rug` тоже считаются на момент `t`.

Это и в живом скоринге, и в бэктесте. В бэктесте `t` = первый шилл + задержка (`--delay-min`, по умолчанию 10 минут).

## История, на которой считается статистика

Исходы — `token_outcomes` с `rule_version = SIGNAL_OUTCOME_RULE_VERSION` (`v2`), горизонт 24 ч, `reference = 'first_mention'` — для шиллеров и похожих случаев. Для креатора — `reference = 'creation'`, горизонт 24 ч.

**Атрибуция исхода шиллеру.** Исход считается от первого упоминания токена кем угодно. Поэтому прошлый токен входит в историю шиллера, только если его первое упоминание этого токена не позже `first_mention_at токена + 60 минут`. Кто написал позже, получил бы «успех» за уже случившийся рост.

**Базовые доли.** `b` — доля `success` среди всех окончательных `first_mention`-исходов, известных на `t`; `b_rug` — то же для `rug`. Если таких исходов меньше 100, берутся `b = 0,05` и `b_rug = 0,3`.

**Сжатая оценка шиллера** (k = 10): `p_shr = (success + 10·b) / (n_final + 10)`, `lift = p_shr / b`; `rug_shr = (rug + 10·b_rug) / (n_final + 10)`, `rug_lift = rug_shr / b_rug`. Новичок без истории получает `lift ≈ 1`, то есть ноль баллов.

## Признаки (как в `features`, ключи на английском)

```json
{
  "scorer_version": "s1",
  "evaluated_at": "2026-10-19T03:12:00+00:00",
  "outcome_rule_version": "v2",
  "horizon": "24 hours",
  "base": {"success_rate": 0.05, "rug_rate": 0.3, "n_final": 40, "default_used": true},
  "token": {"token_id": 1, "mint": "...", "symbol": "WIF", "name": "...",
            "created_at": "...|null", "first_mention_at": "...", "age_minutes": 14.0,
            "entry_minute": 3.5},
  "inside": [
    {"kol_id": 7, "username": "alpha", "followers": 12000, "first_mention_at": "...",
     "minute": 3.5, "n_final": 12, "success": 5, "rug": 1,
     "success_rate": 0.4167, "success_lb": 0.193, "lift": 2.8,
     "rug_rate": 0.0833, "rug_lb": 0.015, "rug_lift": 0.55,
     "onchain": null}
  ],
  "n_shillers": 3,
  "creator": {"wallet": "...|null", "past_final": 4, "past_rug": 3},
  "similar": [
    {"token_id": 9, "mint": "...", "symbol": "XYZ", "similarity": 0.72, "jaccard": 0.67,
     "label": "success", "peak_multiple": 5.1}
  ],
  "components": {"shillers": 19.8, "breadth": 10.0, "creator_clean": 0.0, "entry": 0.0,
                 "similar": 0.0, "rug_shillers": 0.0, "creator_rug": -25.0, "similar_rug": 0.0,
                 "kol_holding": 0.0, "kol_fast_dumpers": 0.0, "kol_sold_after_call": 0.0},
  "evidence": {"best_shiller_n_final": 12, "shillers_with_10plus": 1, "similar_cases": 4,
               "shillers_with_onchain": 0, "shillers_holding": 0},
  "risks": ["creator_rugged_before", "single_shiller"]
}
```

- `onchain` — поведение кошельков шиллера (раздел «Кошельки шиллеров» ниже); `null`, если сделок кошельков шиллера до `t` нет.

- `entry_minute` — минуты от создания токена до первого шилла (null, если `created_at` неизвестен). `minute` у шиллера — от создания токена до его первого упоминания (если создание неизвестно — от первого шилла токена).
- `inside` — разные шиллеры, упомянувшие токен до `t`, отсортированы по `lift` по убыванию. `n_final` и счётчики — по прошлым токенам этого шиллера с окончательной меткой (каждый токен один раз, с учётом правила атрибуции).
- `success_lb`, `rug_lb` — нижняя граница 95% интервала Уилсона (`kairos.report.wilson_lower_bound`), только для показа; в баллы не идут.
- `creator.past_*` — прошлые токены того же кошелька креатора: созданные раньше этого, с `created_at + 24 ч ≤ t` и окончательной меткой от `creation`.
- `similar` — до 5 прошлых токенов с окончательной меткой и сходством ≥ 0,2, по убыванию сходства. Пока только для показа (вес 0).

## Похожие прошлые случаи (только показ, вес 0)

Для прошлого токена P: `S(P)` — шиллеры, упомянувшие P в первые 24 ч после его первого шилла (и не позже `t`); `S(T)` — шиллеры текущего токена до `t`.

- `jaccard = |S(T) ∩ S(P)| / |S(T) ∪ S(P)|`;
- `minute_sim = 1 − min(|entry_minute(T) − entry_minute(P)| / 60, 1)`; если у кого-то минута неизвестна — 0,5;
- `similarity = 0,8 · jaccard + 0,2 · minute_sim`; кандидаты — только с `jaccard > 0`.

Сейчас похожие случаи — это почти те же токены тех же шиллеров, то есть повтор компоненты `shillers`, поэтому в баллы не идут. Включить, когда данных станет больше: `S(P)` за тот же `delay` от первого шилла, кандидаты только при `|S(T)| ≥ 2` и `jaccard ≥ 0,5`, компонента — при `n_similar ≥ 5`.

## Формула s1 (баллы, итог обрезается в 0–100)

Плюсы (в сумме до 85):

| Компонента | Баллы | Как считается |
| --- | --- | --- |
| `shillers` | до 55 | `55 · clamp((max lift − 1) / 4, 0, 1)`; max — только по шиллерам с `n_final ≥ 5`; лучший шиллер в ×5 от базы даёт максимум |
| `breadth` | до 20 | `20 · min(n_shillers − 1, 4) / 4` — один шиллер даёт 0 |
| `creator_clean` | до 10 | 10, если у креатора ≥ 3 прошлых окончательных токена и ни одного рага |
| `entry` | 0 | вес 0, пока бэктест не покажет направление (ранний шилл часто значит бандл или инсайдерский запуск) |
| `similar` | 0 | вес 0, см. выше |

Минусы:

| Компонента | Баллы | Как считается |
| --- | --- | --- |
| `rug_shillers` | до −30 | `−30 · clamp(max rug_lift − 1, 0, 1)` по шиллерам с `n_final ≥ 5`; ×2 от базы даёт максимум |
| `creator_rug` | −15 или −25 | −15, если `past_rug ≥ 1`; −25, если `past_rug ≥ 2` или `past_rug / past_final ≥ 0,5` |
| `similar_rug` | 0 | вес 0 |

`confidence` (сколько доказательств за скором, не «насколько хорош токен»): берётся шиллер с наибольшим `lift` среди тех, у кого `n_final ≥ 5`. `high` — у него `n_final ≥ 30` и ещё хотя бы у одного шиллера токена `n_final ≥ 10`; `medium` — у него `n_final ≥ 10`; иначе `low`.

Коды рисков в `risks`: `creator_rugged_before` (у креатора был раг), `shiller_rug_history` (у кого-то из шиллеров `rug_lift ≥ 1,5` и `n_final ≥ 5`), `single_shiller`, `low_evidence` (`confidence = low`), `late_entry` (`entry_minute > 60`), `unknown_creation` (нет `created_at`), а также `kol_fast_dumper`, `kol_sold_after_call`, `kol_bought_before_call` — поведение кошельков шиллеров, см. ниже.

## Кошельки шиллеров: что они делают на цепи (добавлено 21.10.2026)

Статистика Pump.fun по «callouts»: у топовых авторов медианное время удержания купленного токена — от 9 секунд до минуты, то есть многие КОЛы называют токен и сливают его на подписчиков в первые же секунды. У нас есть сделки кошельков шиллеров (`kol_trades`: Frontrun находит кошельки, Helius отдаёт их сделки), и скор их учитывает.

**Позиция** — кошелёк + mint: от первой покупки до первой продажи после неё (как во view `kol_positions`, миграция `0012`). Закрытая позиция — у которой продажа есть; `hold_s` — её длительность. Всё считается **на момент `t`**: берутся только сделки с `ts ≤ t`, позиция закрыта, если продажа была не позже `t`. Это держит бэктест честным: кошельки опрашиваются раз в час, и живой скоринг отстаёт от цепи, а бэктест — нет, то есть он слегка оптимистичен и здесь (как с `tweet_time`).

По каждому шиллеру токена в `inside[i].onchain` (или `null`, если сделок до `t` у него нет — кошельки не найдены или ещё не опрошены):

```json
{"closed_positions": 12, "median_hold_s": 41.0, "fast_dump_share": 0.75, "fast_dumper": true,
 "first_buy_at": "...|null", "first_sell_at": "...|null",
 "holding": false, "bought_before_call": true, "sold_after_call": true}
```

- `closed_positions`, `median_hold_s`, `fast_dump_share` (доля закрытых позиций короче 60 с) — по всем позициям шиллера, закрытым к `t`, по всем его кошелькам и токенам (включая текущий, если он уже закрыт — это не утечка меток).
- `fast_dumper` — `closed_positions ≥ 3` и `median_hold_s < 120`.
- `first_buy_at` — первая покупка этого токена до `t`; `first_sell_at` — первая продажа после неё (до `t`).
- `holding` — последняя сделка шиллера по этому токену к `t` — покупка (купил и не продавал; продал и докупил; продал часть и докупил). Позиции и медиана при этом считаются по первой покупке и первой продаже, как во view.
- Сигнал пересчитывается и когда в базу попадают новые сделки кошельков по токену (`kol_trades.inserted_at` новее `signals.updated_at`, миграция `0013`), а не только при новых упоминаниях: продажа после поста меняет карточку в ближайший проход скоринга.
- `bought_before_call` — первая покупка раньше его первого упоминания токена (возможный «прогрев»: купил, назвал, продаёт подписчикам). Покупка перед постом сама по себе обычное дело, поэтому это только флаг, без баллов.
- `sold_after_call` — есть продажа этого токена в окне `[первое упоминание, +30 мин]` (и не позже `t`); покупка при этом может быть и не видна (куплено до окна опроса, получено иначе).

Баллы (компоненты `components`, в `risks` — коды):

| Компонента | Баллы | Правило | Код в `risks` |
| --- | --- | --- | --- |
| `kol_holding` | +4 за шиллера, не больше +8 | шиллер купил токен и держит на момент `t` | — (позитивное свидетельство; `evidence.shillers_holding`) |
| `kol_fast_dumpers` | −6 за шиллера, не ниже −12 | шиллер — `fast_dumper` | `kol_fast_dumper` |
| `kol_sold_after_call` | −10 (один раз) | хоть один шиллер продал токен в 30 минут после своего поста | `kol_sold_after_call` |
| — | 0 | первая покупка раньше первого поста | `kol_bought_before_call` |

Веса скромные и временные: кошельков найдено мало (≈1 поиск в сутки при доле 15 % бюджета Frontrun), и калибровать их не на чем; задача — чтобы слив на подписчиков был виден в карточке и чуть опускал скор, а удержание — чуть поднимал. Без данных кошельков все три компоненты равны 0 и скор не меняется. Максимум плюсов становится 85 + 8 = 93, итог по-прежнему обрезается в 0–100. `evidence.shillers_with_onchain` — у скольких шиллеров токена есть данные кошельков.

Бот показывает пометку у шиллера («sold after call», «holding on-chain», «dumps in ~41 s») и коды рисков; объяснения LLM получают `onchain` шиллеров и новые компоненты в фактах.

## Бэктест

- Тестовое множество — токены с окончательной меткой `first_mention` на 24 ч; `no_data` и `pending` исключаются, но их доля указывается в отчёте.
- Все статистики (`b`, `b_rug`, история шиллеров и креатора) пересчитываются на момент `t` каждого токена.
- Метрики: точность и lift (`точность / b`) при порогах 40/50/60/70 и по децилям скора, число сигналов на каждом пороге; доля успехов по корзинам минуты входа 0–10 / 10–60 / 60–180 / > 180 минут — для калибровки `entry`. Порог выбирать там, где точность ≥ 3·b при ≥ 30 сигналах.
- В отчёте — медиана `mentions.first_seen_at − tweet_time` для упоминаний из живого поиска (`frontrun_search`): бэктест видит твиты по `tweet_time`, а живой скоринг — с задержкой сбора, то есть бэктест оптимистичен.

## Потом, когда будут сотни окончательных исходов

- `breadth` считать без известных рагеров (`rug_lift ≥ 1,5` при `n_final ≥ 5`).
- Если max по шиллерам окажется шумным — среднее двух лучших.
- Включить `similar` и `entry` с весами по бэктесту.

## Почему так

- Оценка относительно базовой доли: при базе 1–5 % граница Уилсона почти всегда около нуля, и скор вырождался бы. Сжатие к базе (k = 10) не даёт шиллеру с 1 из 1 обогнать шиллера с 20 из 50.
- Лучший шиллер, а не среднее: один сильный шиллер в токене важнее толпы слабых; толпу учитывает `breadth`.
- Отдельный штраф за раги: успех и раг — не противоположности, у одного шиллера бывают оба.
